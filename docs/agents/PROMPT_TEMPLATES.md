# 任務交辦 Prompt 範本（PROMPT_TEMPLATES）

> 派 subagent 前複製對應範本，填空後送出。`{...}` 是填空處。
> 每份範本都內建三要素（目標與動機 / 驗收條件 / 回報格式）+ 回報合約。
> 派誰、用什麼 model 見 [MODEL_DISPATCH.md](MODEL_DISPATCH.md) §1。

## 共用尾段（每個範本結尾都加這段）

```
回報合約：
- 只回結論與 檔案:行號，不貼大段內容。
- 產物超過 30 行 → 存到 {路徑或 scratchpad}，回傳路徑 + 3 行摘要。
- 失敗時回失敗軌跡：試了什麼、錯誤訊息原文、卡在哪。
- 沒把握的標 [未確認]，禁止編造路徑/參數/名稱。
- 回報上限 {N} 行。
```

## 1. 搜尋（cavecrew-investigator / Explore，model: haiku）

```
目標：找出 {要找什麼：定義/呼叫點/所有用法/設定來源}。
動機：{為什麼要找，主線任務是什麼——讓你判斷哪些命中相關}。
範圍：{目錄或檔案類型，例如 backend/**/*.py；明確排除 data/、node_modules/}。
驗收條件：
- 每個命中給 檔案:行號 + 一行說明它是什麼。
- 找不到也要回報「搜過 {哪些 pattern}，0 命中」，不准猜。
回報格式：表格（位置 | 說明），依相關性排序，最多 {15} 列。
```

---

## 2. 實作（general-purpose 或 cavecrew-builder，model: sonnet）

```
目標：{做什麼功能/修什麼 bug，一句話}。
動機：{使用者原始需求 + 這步在整體中的位置}。
規格：
- {輸入/輸出/行為，越具體越好}
- 遵守 CLAUDE.md 慣例：{列出相關的，例如「HTTP 只走 api/client.js」「邏輯寫 backend/services/ 不 import data_engine」}。
- 只准動這些檔：{清單}。要動清單外的檔 → 停下回報，不要動。
驗收條件（全過才算完成）：
- {可機械檢查的條件 1，例如 curl http://127.0.0.1:8000/api/xxx 回 200 且含欄位 y}
- {條件 2，例如 npm run build 無錯}
- 不留臨時檔與 debug print。
回報格式：改了哪些檔（檔案:行號 + 一行原因）、驗收條件逐條打勾、沒做的事。
```

## 3. 重構（general-purpose，model: sonnet）

```
目標：重構 {對象}，{目的：去重複/抽共用/改結構}。
動機：{現在的痛點}。
不變式（重構前後必須完全相同的行為）：
- {例如：所有 API 回傳 JSON 結構不變}
- {例如：CSV 輸出欄位與順序不變}
先跑基準：重構前先 {跑什麼指令} 記錄輸出；重構後重跑，兩者 diff 必須為空。
範圍：只准動 {檔案清單}。發現要動範圍外才能完成 → 停下回報方案，不要動手。
驗收條件：基準 diff 為空 + {測試/build 指令} 通過。
回報格式：動了哪些檔、基準比對結果原文、行為差異（應為「無」）。
```

## 4. 研究（general-purpose，model: sonnet）

```
目標：回答 {具體問題，可判定「答完了沒」的形式}。
動機：{這答案要拿來做什麼決策}。
來源要求：{官方文件/repo 內程式碼/網路}，每個結論附出處（URL 或 檔案:行號）。
驗收條件：
- 每個問題有答案或明確標「查不到」。
- 區分「文件明說」vs「推論」，推論要標 [推論]。
- 過時風險高的資訊（版本號、參數名）附查證日期。
回報格式：逐題編號作答，每題 ≤5 行 + 出處。總長 ≤{40} 行。
```

---

## 5. 審查（cavecrew-reviewer，model: sonnet）

```
目標：審查 {diff/檔案/分支}，找 {正確性 bug / 規格偏離 / 安全問題}。
動機：{這段程式碼要進哪裡、風險在哪}。
重點順序：{例如 1.安全（auth/secret 洩漏）2.正確性 3.慣例違反}。格式 nit 不要報。
規格依據：{驗收條件或規格所在的檔案路徑，讓審查有對照物}。
驗收條件：每個發現一行：路徑:行號、嚴重度、問題、建議修法。零發現要寫「檢查過 {哪些面向}，無發現」。
你的任務是找碴不是背書——寧可誤報讓我過濾，不可漏報。
回報格式：依嚴重度排序的清單，最多 {20} 條。
```

## 6. 驗證（fresh general-purpose，model: haiku 或 sonnet）

```
目標：驗證 {檔案/改動} 是否符合 {規格所在處}。你沒有做這份產出，用全新眼光讀。
驗收條件：
- 逐條對照規格，每條標 通過/不通過/規格模糊。
- 文件類：指出弱模型會誤讀的句子、互相矛盾的規則、不存在的路徑或工具名。
- 程式碼類：實跑 {指令}，貼輸出原文。
回報格式：規格條目 | 判定 | 證據（引原文或 檔案:行號）。找碴不是背書。
```
