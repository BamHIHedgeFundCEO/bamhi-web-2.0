# 判斷力外化（JUDGMENT_RUBRICS）

> 把「品味判斷」變成可勾選的檢查表。每條附一正例一反例。
> 使用方式：遇到標題描述的情境，逐條勾選，不憑感覺。

---

## R1. 何時升級模型

升級（見 [MODEL_DISPATCH.md](MODEL_DISPATCH.md) §4）的觸發條件，滿足**任一**即升：

- [ ] 便宜模型的回答自相矛盾，或答非所問（不是答錯，是沒對準問題）
- [ ] 任務需要跨 3 個以上檔案/模組同時推理其交互作用
- [ ] 失敗軌跡顯示問題出在「理解」而非「執行」（指令都跑對了，但方向錯）
- [ ] 涉及安全、認證（auth.py、JWT、Supabase key）、金流資料正確性的修改

**正例**：sonnet 兩次都把 `sector_rotation` 的訊號算錯，且兩次錯法不同 → 帶完整失敗軌跡升 opus。
**反例**：haiku 因為 PowerShell 語法錯誤跑失敗 → 這是執行問題不是理解問題，修指令重派 haiku 即可，不升級。

## R2. 何時算真的完成

全部勾完才算完成，缺一項就不准回報「done」：

- [ ] 驗收條件逐條對過（交辦時寫的那幾條，不是自己重新解釋的版本）
- [ ] 產出被 fresh agent 或實跑驗過（文件 read-back / 程式碼跑測試或 curl）
- [ ] 改動範圍內沒有留下臨時檔（`_verify_*.py`、scratchpad 殘留）與 debug print
- [ ] 回報裡寫了「沒做的事」與「已知限制」（沒有就寫「無」）

**正例**：改了 API 端點 → curl 實測回 200 且 JSON 欄位正確 → 貼實測輸出 → 回報完成。
**反例**：「程式碼看起來對，應該可以了」→ 這不是完成，這是還沒開始驗證。

## R3. 何時停下來問使用者

**先自查**：答案能否從 request 原文、程式碼、慣例推出？能就不問。以下情況**必須停**：

- [ ] 要刪除或覆蓋「不是自己這個 session 建立的」檔案，且該檔內容與描述不符
- [ ] 要動生產環境（Render env、Vercel 設定、GitHub secrets、`git push --force`）
- [ ] 兩個合理方案會導致不同的對外行為（API 格式、UI 行為），且原始請求沒指定
- [ ] 觸及 [MODEL_DISPATCH.md](MODEL_DISPATCH.md) §4 的停損線（升級鏈走到底或 opus 已試 2 次仍失敗）
- [ ] 發現使用者的前提可能是錯的（例如要求修的 bug 其實是預期行為）

**正例**：使用者說「刪掉舊戰報」但 `data/` 裡有 3 種命名格式的檔案 → 列清單問哪些算「舊」。
**反例**：不確定變數該叫 `sectorList` 還是 `sectors` → 這種事照鄰近程式碼慣例選一個，不問。

## R4. 什麼訊號代表方向錯（該換路，不是再試一次）

出現**任一**訊號，停止目前路線，回到上一個決策點換方法：

- [ ] 修好 A 弄壞 B，修好 B 又弄壞 A（蹺蹺板）→ 兩者共享的假設錯了，往上找共因
- [ ] 每一步都要加新的特例/hack 才能前進 → 抽象選錯了
- [ ] 錯誤訊息在變，但都指向同一個底層元件 → 直接查那個元件，不要繼續在表層修
- [ ] 你開始想「先硬編碼繞過去之後再回來修」→ 這是方向錯的味道，不是進度
- [ ] 同一個測試/指令你已經完整跑了 3 次以上期待不同結果

**正例**：CORS 錯誤改了 3 種 header 組合都沒用 → 停，檢查是不是根本打錯 URL（後端沒起來）。
**反例**：測試失敗一次，錯誤訊息明確指出少個 import → 這不是方向錯，補上就好。

## R5. 品質底線怎麼驗（最低成本的必做驗證）

按產物類型，這是**底線**不是理想；做不到就在回報標明「未驗證」：

| 產物 | 底線驗證 |
|------|----------|
| 後端改動 | 起本地 server（`AUTH_DISABLED=true`），curl 相關端點，貼 status + body 前 120 字 |
| 前端改動 | `npm run build` 過 + dev server 開頁面確認無 console error |
| pipeline / 資料 | 跑該 script，`pandas` 讀輸出 CSV 驗 shape 與最新日期 |
| 文件 | fresh agent read-back：能否只靠這份文件執行？列出歧義句 |
| 設定/env 改動 | 重啟受影響服務確認起得來（不是只確認檔案存了） |

**正例**：改了 `insider.py` → 本地起 server → `curl /api/insider/...` → 200 + 資料合理 → 貼輸出。
**反例**：「lint 過了所以沒問題」→ lint 不驗行為，不算底線。

---

## R6. 模糊題與品味判斷（誠實條款）

拆解、驗證、多樣本評審補得了「執行品質」，補不了「品味」。遇到以下情況，不要假裝能做：

- 命名、文案語氣、UI 美感、「這功能值不值得做」→ 產 2-3 個候選 + 各自 trade-off，交使用者選。
- 投資邏輯/篩選參數的好壞（如 SCREENING_PLAYBOOK 的門檻值）→ **不是模型能判斷的**，只能呈現數據後果，決策權在使用者。
- 覺得自己在「腦補使用者想要什麼」→ 停，見 R3。
